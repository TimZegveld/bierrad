# Mandatory security and privacy constraints

These requirements apply to code, infrastructure, tests, documentation, CI and local development. Security takes precedence over implementation convenience. The original briefing is retained in `docs/security-guardrails.md`.

## Trust boundary and secrets

GitHub, Git history, Pages, source maps, frontend bundles, browser storage, network addresses and every `VITE_*` value are public/untrusted. Browsers and WebSocket messages are untrusted input. Server authority and service credentials belong behind the Cloudflare boundary. Never ship or commit Slack tokens, OAuth secrets, private API keys, Cloudflare credentials, signing/encryption keys, database/service-account credentials or webhook secrets, including in tests, examples, comments or builds. Use server secret management. Only public endpoint configuration belongs in Vite or Pages CI.

## Temporary access

Live participant data requires a valid, unexpired, scoped capability on every access. Use separate cryptographically random host and spectator capabilities, unrelated to names, timestamps or Slack identifiers. Host capabilities need at least 128 bits. Spectator capabilities only grant viewing and may be 5 words from the fixed 1024-word list (50 bits; explicitly accepted by the owner on 2026-10-02 for shorter links); never lower this further and never use such short capabilities for any write, host or Slack right. An internal ID is not authorization. Store hashes instead of raw capabilities where practical. Capabilities are bearer access, not user identity: anyone holding a link can use its rights until expiry or revocation. Support revocation where practical. Never create public session listings or a global participant endpoint.

Starting a Slack session requires server-side Sign in with Slack (OpenID Connect authorization code flow; requested by the user on 2026-10-02). Bind each attempt to the browser with a short-lived host-only HttpOnly Secure SameSite=Lax cookie holding random `state` and `nonce`; verify state, issuer, audience, expiry, nonce and workspace; keep the client secret server-side and out of URLs. Only full members of the bot's own workspace may start (no guests, external, bot, app or deleted accounts). Revoke the user token immediately and never store Slack identities, profiles or tokens with the session. Login redirects return capabilities only in URL fragments and send no referrer. A login-started session has a fixed Slack ceiling of 30 days plus one hour from its start and loses Slack rights when login, bot or client secrets are removed. Start-link grants are no longer accepted: only sessions started through Sign in with Slack hold Slack rights; any other stored grant fails closed.

Host mutations require server-side authorization, including manually crafted HTTP and WebSocket requests. Spectators only view. The server determines participants, winner count, timing, unique winners, DrawInstruction and reset. Never accept client-supplied official results. Every input requires server validation, size limits and safe error handling. CORS is an explicit allowlist, never an authorization mechanism. Session creation, mutations and draws require abuse controls with honest documentation of limitations.

## Privacy and retention

Default live TTL is 24 hours. At the explicit host request to schedule a draw, an unexpired session may be extended to the scheduled start plus one hour (never shortened); scheduling is bounded to 30 days ahead. Slack sessions may not be extended beyond their currently validated grant expiry or login ceiling. This retention change was explicitly requested by the user on 2026-10-02. Expired sessions must never be revived. Enforce expiry on every server access and socket delivery, invalidate/close sockets and delete expired application state. Never return expired participants. No permanent directory or identifiable history without a separate privacy review. Send explicit allowlisted DTOs with session-scoped participant IDs and display names; never serialize private server models, hashes, credentials or unnecessary Slack IDs. Collect only necessary data. No real employee names, email addresses, Slack messages/IDs, internal URLs, company information or webhooks in repository fixtures; use synthetic data.

Slack remains server-only, with minimal documented scopes when implemented. No browser Slack credentials. Scheduling must use the same authoritative draw operation.

Spectator-link reminder (explicitly requested by the user on 2026-10-02): when scheduling a draw in a Slack-linked session, the host may opt in to have the server post the session's spectator link in the source Slack thread shortly before the start (two minutes, or immediately for shorter plans). This deliberately gives view access to everyone who can read that thread, including Slack Connect members, until the session expires; the host UI says so. The host's browser supplies its own spectator capability; the server only accepts it after matching the session locator and the stored spectator hash, never accepts other links or text, and builds the URL from the server-configured `FRONTEND_URL` with the capability in the fragment only. The raw spectator capability is the one exception to hash-only storage: it is kept server-side only while that reminder can still be posted and is deleted when it settles, is cancelled or replaced, on draw, reset, manual mode and expiry. It never appears in DTOs, logs or errors. Posts are unfurl-free, never broadcast, claimed before I/O, never repeated when delivery is uncertain, retried at most once after a definite rejection, and capped per session.

Channel-bound Koffierad (explicitly requested by the user on 2026-10-05, including the persistent binding, the bearer request link and the extra scopes): a full member of the bot's workspace, verified with the same Sign in with Slack checks, may bind the Koffierad to one public or private channel. The binding is only stored after the bot posts a confirmation in that channel, which proves bot membership; rebinding replaces both links. Per channel the server stores only the channel and workspace IDs, the bot's own user ID, hashes of separate random admin and request capabilities (256 bits each), the raw request capability (it is already posted in the channel; kept so every call can link to the fixed channel page, never returned in DTOs, logs or errors; the fixed link was requested by the user on 2026-10-05), the hash and raw value of the view-only word link described below, the channel name from the last signed `/koffierad` (display only, strictly validated, never used for authorization or lookups; requested by the user on 2026-10-05 so screens show which channel they belong to; it is shown to request, admin and word link holders), the default wait, a daily round counter and, while a round can still be watched, that round's raw spectator capability, plus the review settings and personal links described under "Round reviews" below. It never stores who bound it, who requested a round or any participant data, and never a Slack identity: personal links keep only a pseudonym. This is the one exception to the session retention above: a binding expires 90 days after its last bind or round request, or immediately on unbind, and is then deleted and never revived. The channel's Durable Object name is derived from its channel ID so slash commands can find it; it grants nothing without a capability or a valid Slack signature. Water rounds (explicitly requested by the user on 2026-10-05): the same binding, links, limits and rules also serve water rounds. Each round stores its variant (`coffee` or `water`) and the binding stores the last round's variant so an idle screen keeps its theme; both are non-sensitive, display-only, chosen by the server from the command or an allowlisted request field, and never used for authorization or lookups. Requests without a variant are coffee.

View-only channel word link (explicitly requested by the user on 2026-10-05, for typing on an office screen): each binding also has a separate random 5-word viewer capability from the fixed list (50 bits, the spectator floor above; never lower). It only returns the latest watchable round of that channel (start time, active flag and that round's spectator capability) and accepts no command of any kind, so it can never start rounds or manage the binding. It lives as long as the binding, which makes it the one long-lived 50-bit capability: rebinding and request link rotation replace it, unbind and expiry delete it. The channel stores its hash and its raw value; the raw value is returned only to request and admin link holders (who already hold more rights) so they can read it out. It is never logged or put in errors. Its only Slack use is as the "Kijk live mee" link in each round's call (explicitly requested by the user on 2026-10-05). That gives everyone who can read the channel, including Slack Connect members, view access to the channel's rounds until it is replaced. They already hold the stronger request link from the confirmation message. Because word links carry no locator, a pointer object named by `SHA-256("koffierad-viewer:" + words)[0:32]` stores only the channel's object name; it grants nothing, the channel checks the hash on every access, and a pointer deletes itself once the channel rejects it.

Rounds start only from a signed `/koffierad`, `/waterrad` or `/koekrad` in the bound channel (requested by the owner on 2026-10-06): no channel link, whether admin, request or personal, can request a round, and the channel API refuses any such command with 400. The request capability is bearer access to watch rounds and to start a personal login; the confirmation message posts it in the channel, so everyone who can read that channel, including Slack Connect members, holds it until the admin rotates it or unbinds. The admin capability is returned only to the person binding, in the URL fragment. Each channel allows one active round, coffee, water or cookie, at most 25 per rolling 24 hours shared by all three (raised from 20 by the user on 2026-10-05), and also spend the session creation rate limits. Every round is a new temporary spectator-only session without any host capability, with exactly one winner, expiring one hour after its start. Its server refreshes the reactions at most once a minute (never within 30 seconds of the final check), the bot's own prefilled `:coffee:` (or, for water, `:droplet:`, for the Koekrad, `:cookie:`) reaction never counts, a round counts only its own reaction and the existing final check, draw and thread result apply. The call is a fixed top-level channel message linking to the view-only word link (in the fragment), or to the fixed channel page for bindings without one and for rounds with reviews ("Open de ronde"; the same link is already in the confirmation message, so this adds no audience). Both show the latest round's live wheel and result; the winner result goes to its thread, never unfurled, never broadcast, and never names the requester. Settled call (explicitly requested by the user on 2026-10-06, replacing the earlier winner broadcast so the channel keeps one message per round): once a round is drawn, or ends without a draw, the server rewrites the bot's own call message with `chat.update` (existing `chat:write`, no new scope). The rewritten call contains only the fixed title (for the Koekrad with the validated round word) and start time, the server-frozen winner mention (or name as literal text) with the participant count, or the fixed "nobody joined" or "could not read" notice; it has no link or capability any more, and no thread notice is posted. Only the call whose `ts` the server stored for that round is updated, and the response must name that same message. Updates are claimed before I/O; because an update is idempotent, an uncertain or rejected one may be repeated, at most three times in total. Edits do not notify, so the winner's thread reply remains the mention that does.

Waterrad (explicitly requested by the user on 2026-10-05, including sharing the Koffierad app; restricted to channel rounds by the owner on 2026-10-07): a third variant under exactly the same rules as coffee, but only as a round of a channel-bound Koffierad started with `/waterrad`. It is not a standalone wheel: there is no local water wheel or switcher entry (old `#/water` and `#/water-slack` routes open the Koffierad), `POST /api/sessions` refuses `variant: "water"` and `/auth/slack/water` starts no login. Existing water rounds and their spectator links keep working until they expire. It deliberately uses the Koffierad Slack app and its server-side `COFFEE_SLACK_*` credentials, so it adds no app, scope or secret, and removing those secrets disables water exactly like coffee. The beer app is never used for water. Water counts only `:droplet:` reactions and never another variant's reaction, posts water texts, and its variant is fixed at creation and in the login cookie like every other variant. Local water rosters and preferences use their own `waterrad.*` storage keys.

Sign in with Slack starts only Bierrad sessions (requested by the owner on 2026-10-07): the Koffierad reaches Slack solely through its channel binding. `/auth/slack/coffee` and `/auth/slack/water` start no login, and a plain or join login cookie accepts only the beer variant. The Koffierad app's login is used only to bind a channel and for personal channel links. A local or plain live Koffierad (`POST /api/sessions` with `variant: "coffee"`) stays available without any Slack access.

Koekrad (explicitly requested by the owner on 2026-10-07, including sharing the Koffierad app and the round title): a fourth variant (`cookie`) under exactly the same rules as water, only as a round of a channel-bound Koffierad started with `/koekrad`. It is not a standalone wheel: no local route, switcher entry, plain live session or Sign in with Slack start. It uses the Koffierad app and its `COFFEE_SLACK_*` credentials, adds no app, scope or secret, counts only `:cookie:` reactions (the bot adds its own with the existing `reactions:write`, which never counts) and shares the channel's one active round and daily limit with coffee and water.

Koekrad round title (explicitly requested by the owner on 2026-10-07): `/koekrad [titel] [minuten]`, for example `/koekrad taart 5`, names the round after one word ("Taartronde", "Taartrad", "taarthaler"). It is the only client-chosen text that the server puts into Slack posts and shows on round pages, so it is restricted on the server, independently of Slack's own escaping: after NFC normalization and Dutch lowercasing it must be one word of 2 to 20 lowercase Latin letters (a–z and à–ÿ without ÷) with single inner hyphens. Spaces, digits, punctuation, `<`, `>`, `&`, `@`, `:`, `*`, `_`, `~`, backticks, dots, slashes and invisible characters are refused, so a title can never form a mention, special mention, link, emoji code, formatting or HTML. Anything else gets the ephemeral help text. Only `/koekrad` accepts a word, and the channel object and round session validate it again before storing it. The word is display only: it never authorizes, selects an object, changes the theme beyond its text, or influences winner selection or wheel rendering. It appears only as literal Slack `rich_text` text elements and in the escaped fallback, with `mrkdwn: false` and `parse: none`, and in the frontend only as React text. It is stored only with that round (in the binding while the round can be watched, and in the round's temporary session and its pending Slack jobs until they expire) and is shown to everyone who can already see that round: the channel, link holders and the word link. It is never logged and never put in errors.

`/koffierad`, `/waterrad` and `/koekrad` slash commands, all commands of the Koffierad app sent to the same endpoint, are the only inbound Slack endpoint. They are authorized solely by Slack's HMAC-SHA256 request signature using the server-side `COFFEE_SLACK_SIGNING_SECRET`, with a five-minute timestamp window, a byte-bounded raw body, exact parameters and per-user rate limits; anyone Slack lets use the command in a bound channel, including guests, may start a round. Successful requests get no reply because the call confirms them; other replies are ephemeral and contain no secrets. The extra bot scopes are `reactions:write`, used only to add the bot's own `:coffee:`, `:droplet:` or `:cookie:` to its own call message, and `commands`. Removing `COFFEE_SLACK_CLIENT_SECRET` or `COFFEE_SLACK_BOT_TOKEN` disables binding, rounds and posts; removing `COFFEE_SLACK_SIGNING_SECRET` disables slash commands.

## Koekrad emoji nominations — reviewed exception, 2026-10-07

The owner explicitly requested that each human reacting with `:name-koek:` adds an extra wheel entry for that name, independent of their own `:cookie:` signup. This extends the cookie-only reaction rule above solely for Koekrad rounds. Emoji prefixes must be 1–32 ASCII letters with single inner hyphens or underscores (underscores represent spaces); all other names are ignored. Complete, validated reactor lists are required for every relevant reaction; duplicate reactions, invalid IDs, incomplete lists and more than 100 total reaction entries fail closed. Bots, apps, deleted users, Slackbot and the round's own bot remain excluded. Profiles are fetched once per unique reactor, through existing server-only APIs and scopes.

Each extra entry has a stable random session ID and its own literal display label. Only the temporary round session keeps the emoji/reactor key, sponsor ID and an optional target Slack ID. The target must be the unique case-insensitive exact name match among that round's own `:cookie:` signups, before disambiguation suffixes; never a workspace-directory search, first-name guess, manual name or another nomination. Missing and ambiguous matches stay plain text. Winner and sponsor IDs are frozen server-side at draw time; only the winning extra entry credits its reactor with "Mede mogelijk gemaakt door..." in the existing thread result. This explicitly permits that sponsor mention even when the reactor did not separately sign up. All other text remains literal and escaped; no broadcast, unfurl, new audience or retry behavior is added. No Slack IDs, reaction keys or sponsorship metadata enter browser DTOs, storage, URLs, logs or errors. All private entry and pending-job data disappear with the existing temporary round expiry. An extra entry grants no review vote; a matched winner is reviewed as the actual signed-up Slack user and cannot vote on themselves. Other variants, authorization, limits, renderer and draw authority remain unchanged; no new secret, scope, dependency or migration.

## Round reviews — reviewed exception, 2026-10-06

The owner explicitly requested anonymous 1–5 star reviews with optional text for the winner of a round, posted in Slack and never remembered (2026-10-06), with personal links so people log in once. This section covers coffee, water and Koekrad channel rounds and, since PR 3, sessions started with Sign in with Slack (Bierrad, see the last paragraph). Reviews are optional per channel and on by default, also for existing bindings (requested by the owner on 2026-10-06): the admin sets the default and the window (5, 10, 15 or 30 minutes, default 15, requested by the owner on 2026-10-06; bindings without a stored choice follow this default), every round started with `/koffierad`, `/waterrad` or `/koekrad` follows it. Scores never affect winner selection or rendering, and nothing is kept after the round's session ends.

**Personal links.** Anyone holding a channel link (admin, request or personal) may start Sign in with Slack with the purpose `member-<channel locator>`, bound in the same short-lived host-only HttpOnly Secure SameSite=Lax login cookie. The channel link reaches the backend only in a form POST body of at most 1 KiB, from an allowlisted Origin, never in a URL; the frontend CSP allows forms only to self, the configured backend and slack.com (for the login redirects). The usual OIDC checks apply: state, nonce, issuer, audience, expiry and workspace; only full members of the bot's workspace; the user token is revoked at once. Only this purpose uses the verified Slack user ID, and only to compute a pseudonym: HMAC-SHA256 with a random 256-bit key per binding. The channel stores per personal link only that pseudonym, the SHA-256 hash of a random 256-bit secret and an expiry 30 days after login. There are at most 500 per channel; the link closest to expiry is replaced. At most 30 personal logins start per channel per minute; they spend the request rate limit but not the creation budget. A new login replaces that person's previous link. The raw link is returned only in the URL fragment of the login redirect. A personal link has the request link's rights plus that person's own review and logout, never admin rights. Logout deletes it. Rotating the channel link removes all personal links. Rebinding, unbinding and binding expiry delete them together with the key, after which no stored pseudonym can be linked to anyone. Personal links are bearer access: whoever holds one can watch and cast that person's single vote; the server cannot prove who holds a browser.

**During a round.** The round session temporarily holds the pseudonym key and the channel link (for the call's "Open de ronde"). When the draw starts it computes the pseudonyms of its Slack participants and freezes who may vote: every Slack participant of that draw except the winner. Ballots open one minute after the last reveal (requested by the owner on 2026-10-06), so no ballot names a winner before the wheels stop; the window counts from then. They close when every eligible person has voted or the window ends, always at least a minute before the session expires. Each pseudonym may submit one ballot. Each ballot has exactly one integer from 1 to 5 per reviewable winner (never yourself) and an optional text of at most 280 characters after cleanup (NFC; control characters, bidi overrides and other invisible formatting removed). Extra fields, other draws and late or early ballots are refused. The session keeps only per-winner sums, counts and texts, never per-voter ballots.

**Closing.** At close the session erases every pseudonym, the key and the link. Per-winner averages, counts and shuffled texts remain only until the thread post settles (posted, uncertain or failed); then the texts go too. Everything else goes with the session, one hour after the start. DTOs: shared screens see only the number of eligible people, the number who voted and the closing time. A personal link sees only its own participation and its own ballot (winner display names), plus the same spectator counts as a shared screen; never Slack IDs, pseudonyms or anyone else's vote. Nothing is logged.

**Slack output.** The reviews go out as one reply in the round's thread, never broadcast or unfurled, with `parse: none` and an escaped fallback. Texts are plain text elements, one bullet each in a `rich_text_list`, so mentions, `<!channel>`, links and formatting in them stay literal; only server-frozen winner identities become mentions. The reply is claimed before I/O, never repeated when delivery is uncertain and retried at most once after a definite rejection. Nobody voting means no reply. The call is updated twice: with the deadline and "Open de ronde" while voting is open, then with exactly five star emoji (full, tenths and empty; requested by the owner on 2026-10-06), the average rounded to the same tenth and the count, without any link. Reviews are anonymous: no names, and texts are shuffled. In small groups people may still guess the author; anonymous free text is not moderated and is visible to everyone who can read the channel, including Slack Connect members. The UI says so before voting. No new scope, secret, storage class or migration is added.

**Bierrad sessions (requested by the owner on 2026-10-06).** Sessions started with Sign in with Slack get the same reviews per draw, under these differences.

- **Settings:** the host turns reviews on or off and picks the window (15, 30, 60 or 120 minutes). Reviews are on by default with 30 minutes. Public manual sessions never get reviews.
- **Join link:** the session holds a random HMAC key and a separate random 256-bit join capability. Its hash authorizes. Its raw value is kept server-side inside the join URL, built from `FRONTEND_URL`, until the session ends. That URL is posted only in the session's own Slack thread: in the winner post ("Open de ronde") and, when the host opted into the reminder, in the reminder instead of the spectator link. It is never returned in any DTO, log or error. This deliberately gives everyone who can read that thread, including Slack Connect members, view access to the session until it ends, like the opt-in reminder. The host UI says so, and turning reviews off stops posting it.
- **What the links can do:** the join link and personal links watch exactly like spectator links (HTTP and WebSocket) and can never run host commands. The join link may also start a personal login: a form POST to `/auth/slack/join`, under the same rules as the channel login. Its cookie purpose `join-<variant>-<session locator>` selects that session's own Slack app. Personal links store a hash and a pseudonym in the session, at most 500 per session, replaced on a new login, deleted on logout, and erased with the session.
- **Who votes:** every Slack participant of that draw may review every other Slack winner, never themselves. Manual names neither vote nor get stars.
- **Re-draws:** a new draw cancels a review that is still open; its votes are dropped and nothing is posted. While a review post is pending, new draws and resets wait, as they do for the winner post.
- **Slack output:** the parent message belongs to a person and is never edited. The winner post and the review post are separate thread replies, never broadcast.
- **Locator:** sessions learn their own object name from the Worker. It grants nothing.

## Browser, transport and output

Production uses HTTPS/WSS. Treat names as text; never use unsafe HTML rendering. Never store credentials/capabilities in localStorage, sessionStorage, IndexedDB or JavaScript-accessible cookies. Standalone manually entered names and harmless preferences may remain local; live/Slack rosters must never be automatically stored there.

Prevent capability leakage through URLs sent to third parties, referrers, logs, analytics, screenshots and error messages. Private responses require no-store, noindex and no-referrer controls where supported; document static-host limitations. Review CSP and third-party resource use. Do not add analytics to private views without review. Never log authorization headers, capabilities, full capability-bearing URLs, secrets or environment dumps. Minimize participant data in diagnostics. Errors must not disclose stack traces, private configuration or authorization internals.

## Repository and verification

Ignore local environment/secrets files including `.env`, `.env.local`, `.env.*.local` and `.dev.vars*`; allow placeholder-only `.env.example`. Minimize and review dependencies. No private session data may go to unrelated services. If a credential is discovered, report only its location/type/tracked status; revoke/rotate, investigate and clean history as appropriate. Deleting a line does not remedy exposure.

Changes to APIs, sessions, integrations, authorization, infrastructure or CI require an explicit review against this document, tests, type checking, configured linting, production builds, diff review and searches for credentials, company/employee data and unsafe Vite variables. Report unresolved constraints; never silently weaken them.

> Assume GitHub, GitHub Pages and every browser are completely public and untrusted.
>
> Credentials and privileged operations belong behind the server-side security boundary.
>
> Employee data is only exposed to authorized temporary sessions, using high-entropy, scoped, expiring capabilities.
